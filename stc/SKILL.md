# STC 简明技术性中文

按本 skill 生成、改写和审阅中文。所有规则、词表和检查工具均已包含在本目录中，无须访问外部资料。

## 默认要求

- 用完整句子和自然语序，直接回答问题或交付结果。
- 删除客套、重复和无关解释，信息足够时停止。
- 保留事实、数字、名称、否定词、权限和真实不确定性。
- 按任务需要展开，不得为了简短删掉必要步骤、例外或风险。
- 交付成品时先写采用的结果，制作与复核记录放在内部。
- 任务回执按 C10 分为“做完了”“需要你”“知会”，用户动作单独列出。

## 第一步：判断场景

按读者和用途选择场景。一次任务包含多类文字时，必须分别处理。

| 读者和用途 | 场景 | 规则文件 |
|---|---|---|
| 正在对话的人，读 agent 的回复 | for chat | `rules/for-chat.md` |
| 人，读来理解内容或照着操作：报告、方案、手册、周报、会议纪要、代码注释、提交说明 | for document | `rules/for-document.md` |
| 产品用户，在网页或应用界面看到：按钮、标签、提示、报错、通知、空状态 | for web dev | `rules/for-web-dev.md` |
| agent，读来照着执行：系统提示词、AGENTS.md、CLAUDE.md、skill、工作流程 | for instruction writing | `rules/for-instruction-writing.md` |

读者和用途不清时：读者是模型，用 for instruction writing；读者是产品用户，用 for web dev；其余用 for document。场景判断用于内部执行，用户询问方法时再说明。

## 第二步：读取本地规则和词表

1. 读取 `rules/for-all.md`，再读取选定场景的规则文件。场景规则与通用规则不一致时，以场景规则为准。
2. 读取 `dictionary/avoid.yaml`，只使用 `profiles` 为空或包含当前场景的条目。
3. 写界面文字或“警告、注意、说明”时，读取 `dictionary/recommended.yaml`，按词义使用动作词和提醒级别。
4. 项目有术语表时，必须优先使用项目术语表中的名称。术语表文件名通常含 `terms` 或“术语”，格式可参考 `dictionary/terms.example.yaml`。

规则编号和场景索引见 `rules/README.md`，词表字段说明见 `dictionary/README.md`。

## 第三步：生成、改写或审阅

### 生成

按通用规则、场景规则和词表写作，再完成语义复核。

### 改写

保留原意和以下内容：

- 事实、数字、单位、专有名称、引语、否定词和限定词。
- “可能、也许、大概、通常、偶尔、经常”等表示把握程度或频率的词。
- 代码、命令、文件路径、接口名和错误原文。

程度词和模糊量词必须换成有依据的数字或具体事实。原文和上下文没有依据时，不得编造；删除该词，或写“【待补：需要的事实】”，并在结果后集中列出待补项。

默认只交付改写稿。用户要求解释，或改动会影响使用判断时，再说明主要改动与依据。

### 审阅

先给报告和具体改法，用户要求改写时再给修改稿。写回文件必须有用户授权。

报告按以下顺序组织：

1. 用一句话概括主要问题，区分需修改项与待确认项。
2. 按原句分组，给出位置、原句、问题原因和具体改法，规则编号放在说明后。
3. 单独列出需要用户补充的事实，缺失信息用“【待补：…】”标记。
4. 列出可选改法。用户已选定的修改可以直接执行，不必重复确认。

不得直接把命令输出当作审阅报告。必须结合上下文判断指代、术语、事实和句意，警告经上下文确认后才能判定为问题。

## 第四步：复核

交付前逐项检查：

- 每句话都帮助当前读者理解、判断或操作；多余排除、制作说明和自证已删除（G20）。
- 同一个东西只用一个叫法，项目专有名称与术语表一致（G1、G2）。
- 没有“进行、加以、予以、作出、开展”加动作名词（G4）。
- 程度词和模糊量词已换成有依据的数字或具体事实（G5）。
- 没有营销词、行话、套话和口号句式（G6、G7）。
- 一句只讲一件事，一句宜不超过 40 个字（G9、G12）。
- 否定词、限定词、把握程度和频率没有被删掉或弱化（G14、G15）。
- 句子自然、语法完整，篇幅满足任务，必要步骤和风险信息完整（G21、G22）。
- 页面实际显示的标题、正文、按钮、提示、图注和角标已逐项审阅（W9）。
- 对话没有重复结论、工具旁白或不必要的模板；任务回执符合 C10（C7、C8、C9、C10）。
- 人称符合场景：for document 和 for web dev 不用“我们”“你们”；for web dev 也不用“他”“她”“它”“大家”（D1、W1）。
- for instruction writing 的强度词只有“必须、不得、宜、不宜、可、不必、能、不能”（I1）。
- 数字用阿拉伯数字并带单位；中文与英文、数字之间空一格（G18、G19）。

对本次任务写出的文件或用户指定的材料，环境有 Node.js 18 以上版本时运行本地检查工具：

```bash
node <本 skill 目录>/tools/check.mjs <文件或目录> --profile <场景> --anti-echo
```

场景参数为 `for-chat`、`for-document`、`for-web-dev` 或 `for-instruction-writing`。文字不在文件中时，可通过标准输入传入。错误必须全部修正；Anti-Echo 疑点必须结合读者和用途改写，或为必要内容记录具体保留理由。文本变动后必须重新检查。命令选项和复核文件格式见 `tools/README.md`。

## 不改动的内容

- 引语和用户原话，包括其中的人称。
- 代码、命令、文件路径、接口名。
- 品牌口号和法律文本。
- 英文文字；STC 只处理中文。
